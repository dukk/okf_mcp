## Review round 1 (PR #667)

- `CatalogMeta` carries the catalog's `name`, so creating a catalog drops a
  cached "no such catalog" entry (the new id maps to nothing yet).
- Invalidation epochs exist only while a load is in flight. An invalidation
  of an uncached key keeps no state, so the map no longer grows with the
  population. Minimum generations follow the same rule.
- Every in-place catalog refresh re-inserts the cache entry
  (`Bounded::reweigh`), because moka weighs only on insert, and a catalog
  that grows past the budget is evicted.
- A request pins the snapshot (`Arc<Loaded>`), not only the `CatalogState`,
  so two reads in one request see one generation even across an in-place
  refresh.

## Review round 2 (PR #667)

- **Task order.** Task 10 (listings) now runs before Task 8 and needs only
  Tasks 5 and 7, so it removes the listing enumerations of the catalog map
  before Task 8 deletes the map. Task 8 also takes the per-catalog gauges
  and the `/healthz` count (formerly in Task 16). Task 9 now needs Task 8,
  for its measured weigher. New waves:
  `5 (1, 4)` and `15 (14)` in wave 2; `10 (5, 7)` and `11 (2, 3, 5)` in wave 3;
  `8 (2, 5, 6, 7, 10)`, `12` and `13` in wave 4; `9 (8)` and `16` in wave 5.
- **Indirect invalidations** (`invalidate_where`: credential by hash, users by
  team, the directory by id) raise a fence counter for the whole cache, so a
  load in flight is not cached. Tests hold a load across a revocation and
  across a team change.
- **Settings revalidate after `credential_ttl`** (`App::fresh_settings`, one
  load at a time), so a lost settings notification is bounded like a lost
  credential one.
