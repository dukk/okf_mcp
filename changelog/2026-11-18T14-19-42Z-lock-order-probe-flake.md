## Added
- Test `maintenance_final_lock_probe_ignores_stale_activity_text`, which freezes a probe transaction's `pg_stat_activity` snapshot before a session blocks on an advisory lock. It checks that the old query-text check reports the stale statement (the issue #372 failure) and that the new probe reports the advisory lock and its keys.

## Changed
- The replacement-import race tests (`maintenance_final_submit_coordinates_replacement_import` and `maintenance_final_claim_coordinates_replacement_import`) find the waiting session and its lock in `pg_locks` through a new helper, `wait_waiter`, instead of reading `pg_stat_activity.query`. They now assert that maintenance waits on this catalog's advisory lock (`locktype` `advisory`, keys `CATALOG_LOCK_NAMESPACE` and the catalog id) behind the import. The old `wait_blocked` helper is gone.
- `catalogs::CATALOG_LOCK_NAMESPACE` is `pub(crate)` so the tests can name the key.

## Notes
- Root cause (issue #372): `pg_stat_activity` takes `query` and `state` from a snapshot made once per transaction, but reads `wait_event_type` and `pg_blocking_pids` live. A pooled connection that was idle when the snapshot was taken, and blocked behind the import by the time its row was read, showed the last statement it had run: the test's own `SELECT pid FROM pg_stat_activity ...` lookup, which had run on the same pooled connection. The assertion then read that text. Production code is unchanged.
- The production lock order is correct. `reports::submit` and `runs::claim` both open their transaction with `maintenance::lock`, whose first statement is `catalogs::lock` (`pg_advisory_xact_lock`), then the catalog row (`FOR KEY SHARE`), `maintenance_state` (`FOR UPDATE`), run and work rows, then the cited documents in path order (`FOR SHARE`). `import` locks the audit people (users), takes the same advisory lock through `catalogs::lock_by_name`, then writes documents. Maintenance takes no lock before the advisory lock, so it cannot hold anything the import needs.
- Checked by injecting a frozen snapshot into the race test: with the old query-text check both race tests fail with the issue's exact message; with `wait_waiter` they pass. Checked that the new assertion still detects an inversion by temporarily adding `LOCK TABLE documents IN SHARE MODE` before the advisory lock in `maintenance::lock`: both race tests fail with "maintenance waits on ... locktype: \"relation\"".
