# Milestone 15: observability (close-out, M15 Task 11)

Epic #460. This entry closes the milestone: it records the pull requests
that built it, what differs from the plan, the follow-ups, and a smoke test
of `okf-mcp serve` against a local OpenTelemetry Collector. The task's own
changes (docs, examples, the dashboard test) are listed under Added.

## Added

- `docs/operations.md`: the `[telemetry]` keys in the section 3 table and
  TOML example, the OTLP and `OTEL_*` variables in "The environment", the
  Deployment's `metrics` port, `OKF_OTLP_HEADERS` and downward-API
  `OTEL_RESOURCE_ATTRIBUTES`, and a "Telemetry" section: receivers, Sentry, a
  collector, the metrics listener, tuning stderr, what is never exported and
  why stderr stays sensitive, and the metric and span references (written

  tool calls and p95, publish duration, poll duration and failures, sign-in
  attempts, mail jobs and queue, export failures, clock offset).

  fields is an exported family; a renamed metric fails it.

  server can export, and a unit test that records one event of each kind and
  asserts the rendered families equal the list (the four gauges that need a
  loaded `App` are checked by their own tests).

## Notes

### Deviations from the plan

Each task's plan section has its own dated "Corrected" notes; the ones that
change what an operator sees are:

- A console session's `okf.key.id` is the word `session`, never
  `session:<user name>` (#464).
- OTLP layers take an allow-list of this crate's targets, not a deny-list of
  dependencies (review of the plan's PR).
- `Metrics::FAMILIES` is only the families present before traffic;
  `ALL_FAMILIES` (this task) is the full list.
- `okf.archive.size` renders as `okf_archive_size_bytes_total`.
- Prometheus label names have underscores (`http_route`), unlike the OTel
  attribute names in spans.
- The `mcp <tool>` span is a root trace of its own, not a child of the
  `POST /mcp` request span (see the smoke test).

### Follow-ups

- #495: OTLP export from `okf-maintenance`, deferred by the spec's Non-goals
  and needing its own privacy review (rmcp traces there can carry evidence
  and tokens).
- The `mcp <tool>` span does not join the request's trace. Nothing in the
  spec asked for it to, and the docs say so; if a joined trace is wanted it
  is a design change, not a bug fix, and is not filed.

### Smoke test

Run on 2026-11-16 against the code on this branch, with the debug build of
`okf-mcp serve`, a throwaway `postgres:17-alpine` container, and
`otel/opentelemetry-collector:0.120.0` (a `debug` exporter,
`verbosity: detailed`, on every pipeline). Everything bound to `127.0.0.1`;
the receiver is `http://127.0.0.1:4318`. Both containers and the server were
stopped and removed afterwards. No image build was run: `cargo run -- serve`
is the path the plan allows. The test credentials are throwaway values, and
none appear here.

Setup (`$DB` is `postgres://postgres:<password>@127.0.0.1:<port>/postgres`):

```sh
docker run -d -p 127.0.0.1:55433:5432 -e POSTGRES_PASSWORD=<password> postgres:17-alpine
docker create -p 127.0.0.1:4318:4318 otel/opentelemetry-collector:0.120.0 \
  --config /etc/otelcol/config.yaml          # then: docker cp collector.yaml <id>:/etc/otelcol/config.yaml
docker start <id>
export DATABASE_URL=$DB
okf-mcp migrate
okf-mcp user create alice
okf-mcp user set-email alice alice@example.com
okf-mcp user set-admin alice
okf-mcp catalog create notes --owner alice
okf-mcp key create smoke --user alice --access admin --catalogs notes   # prints the key once
OKF_OTLP_HEADERS=none okf-mcp serve --config smoke.toml
```

`smoke.toml` (placeholders only):

```toml
listen = "127.0.0.1:8099"
allowed_hosts = ["localhost", "127.0.0.1"]
default_catalog = "notes"
public_url = "http://127.0.0.1:8099"
poll_interval = "5s"

[mail]
provider = "log"

[telemetry]
environment = "smoke"

[telemetry.stderr]
format = "json"

[telemetry.otlp]
endpoint = "http://127.0.0.1:4318"
headers_env = "OKF_OTLP_HEADERS"
export_interval = "10s"

[telemetry.prometheus]
listen = "127.0.0.1:9464"
```

Startup (stderr, JSON): `mail provider is "log": messages, links included,
go to the log`, then `serving` on `127.0.0.1:8099`. `/metrics` answered on
`127.0.0.1:9464` at once.

**One MCP call.** `initialize` with the key as a bearer token (200, then
`notifications/initialized` 202), then `tools/call` `list_catalogs`: 200 with
the `notes` catalog. The collector printed:

```
Name           : mcp list_catalogs        Kind: Server   Status code: Unset
     -> okf.tool: Str(list_catalogs)
     -> okf.catalog: Str(none)
     -> okf.key.id: Str(<key id>)
     -> enduser.id: Str(<user id>)
     -> okf.outcome: Str(ok)
```

The `POST /mcp` request spans arrived as their own traces with
`http.request.method`, `http.route` and `http.response.status_code`. The tool
span is a separate root trace from the request span (rmcp runs the call on
its own task).

**One console sign-in.** `okf-mcp user invite alice` queued a setup mail;
the running server's `log` provider wrote the link (a local-only line, as
documented), `POST /account/setup` set a password (303), and `POST /signin`
with `Sec-Fetch-Site: same-origin` answered `303 Location: /ui/`. A second
`POST /signin` with a wrong password answered 401. The collector printed
`POST /signin` with `http.route: /signin`, `http.response.status_code: 303`,
a `sign-in attempt` span event, an `okf.mail.job` span for the setup mail
(`okf.mail.template: setup`, `okf.mail.provider: log`, `okf.outcome: sent`),
and the log records `sign-in attempt` and `console session started`.

**`trace_id` matches stderr.** The `POST /signin` span's trace id is on four
stderr lines, for example:

```
{"message":"sign-in attempt","method":"password","outcome":"ok","level":"INFO","target":"okf_mcp::store::sign_in_events","trace_id":"70c1ef7c...","span_id":"3b270bf7..."}
{"message":"sign-in attempt (detail)","ip":"127.0.0.1","level":"INFO","target":"okf_mcp::local_only","trace_id":"70c1ef7c...","span_id":"3b270bf7..."}
```

The exported half of the event has no address; the `local_only` twin stays
on stderr. The `okf.mail.job` trace id is on two stderr lines.

**`curl 127.0.0.1:9464/metrics`**, trimmed:

The scrape had 15 families; `okf_publish_*`, `okf_lint_*`, `okf_keycache_*`,
`okf_oauth_*`, `okf_ratelimit_*`, `okf_clock_*` and `okf_archive_*` appear
only after their first event (no publish, no OAuth, no `time_server` and no
archive in this run), which the operations guide says. The names, labels and
the `_total` and `_seconds` suffixes in its metric reference match the scrape
for every family that appeared. The collector also received the metrics push
(`okf.build.info`, `okf.mcp.tool.duration`, ... under their dotted names).

**SIGTERM.** One more `initialize` call, its metrics scrape, then
`kill -TERM <pid>`: the process was gone 0.1 s later, having logged `shutting down`,
and the collector's `POST /mcp` span count went from 6 to 7, so the last
batch was flushed (limit 4 s).

**Not run:** the Kubernetes manifests were not applied (no cluster; the
kind smoke test is a nightly job), the ServiceMonitor and Grafana dashboard
were not loaded into Prometheus or Grafana (neither runs here; the dashboard
is checked only by `tests/grafana_dashboard.rs`), and no Sentry or
`sample_ratio` run was made.
