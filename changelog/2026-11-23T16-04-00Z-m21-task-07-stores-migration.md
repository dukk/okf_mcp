# M21 Task 7: migration 0036 (stores, placement, registry columns) and the folder move

## Added
- Five account migrations. Each lock-taking `ALTER` is alone in its file, so its lock is held only until that file commits (sqlx runs each file in one transaction).
  - `0036_stores.sql`: `stores` (one row per database catalog data can live in): `name`, `location_kind` (`account-database` or `host`), `host`, `port`, `database`, `credential_kind` (`iam`, `secrets-manager`, `env`), `credential_ref`, `created_at`. Two table CHECKs tie the kind to the columns: an account-database row has none of host, port, database, credential kind or reference; a host row has all five. The table holds a reference to a credential, never a credential. A `main` row (`account-database`), the only one allowed (`stores_one_account_database`), and one row per `lower(host)`, port and database (`stores_one_row_per_database`). The `default_store` setting, `"main"`, `ON CONFLICT DO NOTHING`. `teams.store` (nullable, `teams_store_fkey` to `stores`, `ON DELETE RESTRICT`): a team's pin.
  - `0037_catalog_placement.sql`: `catalogs.store` (`NOT NULL DEFAULT 'main'`) and `catalogs.provisioned_at` (`DEFAULT now()`), with `catalogs_store_fkey` (`ON DELETE RESTRICT`).
  - `0038_stores_audit.sql`: audit target kind `store`: `audit_entries_target_kind_check` lists it, and `audit_entries_target_shape` has a `WHEN 'store'` arm (a name, and no team, credential or person reference). The shape CHECK's text is 0012's with that one arm added.
  - `0039_stores_validate.sql`: validates the two foreign keys and the two audit CHECKs.
  - `0040_catalogs_unprovisioned_index.sql` (`-- no-transaction`): `catalogs_unprovisioned` on `created_at` where `provisioned_at IS NULL`, built `CONCURRENTLY`; the name is added to `CONCURRENT_INDEXES` in `src/db.rs`, so a failed build is dropped and retried like 0025's.
- `tests/fixtures/migration_history_0035.txt`: the version, description and SHA-384 checksum of each of migrations 0001-0035, taken before the move.
- Tests in `src/db.rs`: `moving_the_migrations_folder_keeps_their_history`, `migration_0036_puts_every_catalog_on_main_provisioned`, `a_release_one_create_after_0036_lands_on_main_provisioned`, `stores_refuses_a_host_row_without_a_credential_reference`, `stores_refuses_an_account_database_row_with_a_host`, `a_second_account_database_store_is_refused`, `a_second_row_for_the_same_host_port_and_database_is_refused`, `a_store_cannot_be_removed_while_a_catalog_or_team_uses_it`, `a_store_cannot_be_removed_while_only_a_team_pins_it`, `audit_entries_accept_a_store_target_by_name_only`, `the_registry_constraints_are_validated_and_the_index_is_built_concurrently`.

## Notes
- **The move changes no history.** sqlx records and compares a migration's version, description and checksum (SHA-384 of the file text), none of which involve the folder. The test migrates a database to 0035, checks its `_sqlx_migrations` rows against the fixture taken before the move, runs the server's `migrate`, and checks the rows again; a mismatch would make `migrate` fail with a version mismatch.
- **Locks, statement by statement** (review of PR #992 found the first draft held `teams` and `catalogs` ACCESS EXCLUSIVE through a backfill `UPDATE`, an index build and a wait for the audit table; it is restructured, and this is read from the final SQL). Nothing rewrites or scans `catalogs`, `teams` or `audit_entries` under ACCESS EXCLUSIVE, and no file takes ACCESS EXCLUSIVE on two existing tables (0039 validates under SHARE UPDATE EXCLUSIVE, which blocks neither reads nor writes).
  - 0036: `CREATE TABLE stores`, its inserts and indexes (a new table, no waiters; the `server_settings` insert takes row locks on that table only). Then `ALTER TABLE teams ADD COLUMN store ... ADD CONSTRAINT teams_store_fkey ... NOT VALID`: ACCESS EXCLUSIVE on `teams` (and SHARE ROW EXCLUSIVE on `stores`), for the instant the statement takes. A nullable column with no default is metadata-only, and NOT VALID skips the foreign key's scan of `teams`. It is the last statement, so the lock ends when the file commits.
  - 0037: one `ALTER TABLE catalogs` adding both columns and `catalogs_store_fkey ... NOT VALID`: ACCESS EXCLUSIVE on `catalogs` for an instant. Both defaults are not volatile (`'main'`, and `now()`, which is STABLE), so PostgreSQL 11 and later store the default in the catalog and rewrite no row; there is no backfill `UPDATE`. Existing rows read as `main`, provisioned at the moment 0037 ran. The plan had them provisioned at `created_at`; nothing reads that as a creation time, only whether it is NULL. NOT VALID skips the foreign key's scan of `catalogs`; new rows are checked at once.
  - 0038: drops and re-adds the two audit CHECKs NOT VALID: ACCESS EXCLUSIVE on `audit_entries` for an instant, with no scan of the log.
  - 0039: four `VALIDATE CONSTRAINT`s, each SHARE UPDATE EXCLUSIVE on the table it scans (plus ROW SHARE on `stores` for the foreign keys), so reads and writes go on while rows are checked (the pattern of 0032). Every row passes: all catalogs are on `main`, no team is pinned, no audit row has the new kind.
  - 0040: `CREATE INDEX CONCURRENTLY`: SHARE UPDATE EXCLUSIVE, writes continue. It is its own `no-transaction` file with this one statement.
  - No `SET lock_timeout`: no earlier migration sets one, so this follows them. A file that waits for a lock queues later writers behind it, as every earlier `ALTER` did; each lock here is the only one its file takes, which keeps that wait short.
- **Rolling deploy (P11).** A release-1 replica's `INSERT INTO catalogs` names neither new column and so lands on `main`, provisioned; `a_release_one_create_after_0036_lands_on_main_provisioned` runs that statement. An older replica ignores the new columns on teams and catalogs, and writes no `store` audit entry.
- Nothing reads `stores`, `teams.store` or `catalogs.store` yet; Task 8 adds the registry in code.
