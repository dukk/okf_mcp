# Milestone 17: display names (epic #597)

Users, teams and catalogs keep their permanent slug ids and gain an editable
display name. The server and the console show people a label (the display
name, else a fallback) and use the id for every call, URL and stored
record. Design: `docs/superpowers/specs/2026-11-17-okf-display-names-design.md`;
plan: `docs/superpowers/plans/2026-11-17-okf-mcp-m17-display-names.md`;
operator reference: `docs/operations.md`, "Display names and labels".

## Operational notes

- **Deploy the MCP runner and the server together.** The runner (the
  investigator, with `src/investigator/contract_tools.json` re-captured)
  pins tool schemas that gained label fields.
- **Rolling upgrade and migration 0019.** The migration locks `users` and
  `teams` while it cleans names and adds the CHECK constraints. During a
  rolling upgrade, old v0.21 replicas can return 500 for names over 80
  characters, and can still store control characters until they are
  replaced.
- **Audit label lookups.** A team label in the audit log is found by the
  immutable team id; a catalog label by `catalogs.created_at` (the log
  keeps no catalog id), so a recreated catalog never lends its label to
  older entries.
- **Export filename.** The server names an export `<stem>-<id>.tar.gz`,
  where the stem is the label with ASCII letters and digits lowercased,
  other runs replaced by `-` and the result cut at 40 bytes ("Work Notes"
  gives `work-notes-<id>.tar.gz`); with an empty stem it is `<id>.tar.gz`.
  The console uses that name from `Content-Disposition`.
- **Console pickers** add the slug, repeatedly, until the option texts are
  distinct (after the owner team, where that separates them).
- **Display-name inputs have no `maxlength`.** The server counts Unicode
  scalar values (80 at most), so the console leaves the limit to it.

## Smoke test (by hand, 2026-11-18T01:07Z)

Debug build of this branch's `okf-mcp` (version 0.21.0, at 215173b) against a
throwaway `postgres:17-alpine` container (`scripts/test-pg.sh up`, bound to
127.0.0.1) and one `okf-mcp serve --listen 127.0.0.1:18091`. Keys were
generated into files under `target/` and are redacted below; the container and
the server were removed afterwards. Logs: `target/gaps-logs/` (not committed).

**(a) Migration 0019 on pre-M17 data.** A binary from before M17 was not built.
Instead the full schema was migrated, then rolled back to the pre-0019 state
by hand (`DROP CONSTRAINT` on `users` and `teams`, `DROP COLUMN
catalogs.display_name`, `DELETE FROM _sqlx_migrations WHERE version = 19`),
and dirty names were written in, then `okf-mcp migrate` ran. This reproduces
the pre-0019 schema and data, not an old binary's writes. Result:

| Row | Before | After |
|---|---|---|
| user alice | 18 chars: leading spaces, NBSP, TAB inside, U+3000 and a space at the end | 13: `Alice Example` |
| user bob | 100 x's | 80 x's |
| user carol | 16: a C1 control (U+009F) and an LF inside | 16: `Carol Line Break` |
| team acme | 100: `Team ` x 20 | 79 (cut at 80, the trailing space then trimmed) |

Last migration 18 then 19; `users_display_name_length`,
`teams_display_name_length` and `catalogs_display_name_length` exist and
`catalogs.display_name` is `text`; `UPDATE users SET display_name =
repeat('y', 81)` was refused by `users_display_name_length`.

**(b) CLI.**

    okf-mcp catalog create work-notes --owner acme --display-name "Work Notes" --description "Team notes"
      created catalog work-notes
    okf-mcp user update alice --display-name "Alice Example"
      updated user alice display name: "Alice Example" -> "Alice Example"
    okf-mcp user update bob --display-name ""
      updated user bob display name: "xxxx...(80)" -> ""
    okf-mcp team update acme --display-name "Acme Team"
      updated team acme display name: "Team Team ..." -> "Acme Team"
    okf-mcp catalog update plain --display-name "Plain Catalog"
      updated catalog plain display name: "" -> "Plain Catalog"
    ... --display-name <81 chars>   Error: display name refused: it is longer than 80 characters
    ... --display-name "bad<LF>line"  Error: display name refused: it holds a control character or a line break
    okf-mcp team update alice --display-name x
      Error: a personal team's label follows its user; change the user's display name

**(c) REST, with API keys** (`Authorization: Bearer <REDACTED>`):

| Request | Result |
|---|---|
| `PATCH /api/v1/users/bob {"display_name":"Bob Builder"}` (admin key) | 200, `"label":"Bob Builder"` |
| `PATCH /api/v1/users/bob`, 81 characters | 422 `{"error":"LimitExceeded","message":"display name refused: it is longer than 80 characters","limit":"display_name"}` |
| `PATCH /api/v1/teams/acme {"display_name":"Acme Inc"}` | 200, `"label":"Acme Inc"`, member `alice` labelled `Alice Example` |
| `PATCH /api/v1/teams/alice` (a personal team) | 409 `Refused`: "a personal team's label follows its user; change the user's display name" |
| `PATCH /api/v1/catalogs/work-notes {"display_name":"Work Notes"}` | 200, `previous_display_name` and `display_name` returned |
| `PATCH /api/v1/catalogs/plain {"display_name":"Plain Jane","description":"A plain one"}` | 200, `"label":"Plain Jane"` |
| `PATCH /api/v1/me` with a user's key | 403 "this needs a console session" (the designed refusal for a key) |

`PATCH /me` with a console session (the 200 path) was **skipped**: it needs a
signed-in console session, which this key-only run did not set up; the route
tests (`patch_me_sets_my_display_name_and_refuses_the_rest`) and the console
end-to-end test cover it.

**(d) `GET /api/v1/labels`.** With the admin key: every user, team and
catalog (`"catalogs":{"plain":"Plain Jane","work-notes":"Work Notes"}`, a user
with no display name is `Unnamed user`, a personal team `Alice Example's
team`). With alice's key (write on `plain` and `work-notes`): only her own
user, her teams (`acme`, `alice`) and those two catalogs. With bob's key
(`plain` only): his own user, his own and alice's personal teams (alice owns
`plain`), and `plain`.

**(e) New catalog heading.** Created `heading-a --display-name "Heading A"` and
`heading-b` (none). Read through MCP `read_document` on `index.md`: `# Heading
A` and `# Catalog`.

**(f) Export filename** (`GET /api/v1/catalogs/<name>/export`, header only):

    work-notes  -> attachment; filename="work-notes-work-notes.tar.gz"
    plain       -> attachment; filename="plain-jane-plain.tar.gz"
    heading-b   -> attachment; filename="untitled-catalog-heading-b.tar.gz"

**(g) Audit** (`okf-mcp audit export`, display-name entries): `details` is
`{"length": n}` only (for example 10 for "Plain Jane", 8 for "Acme Inc", 11 for
"Bob Builder", 0 for the cleared name), with no text. `target.target_label` is
set for `catalog` and `team` targets (`"Plain Jane"`, `"Acme Inc"`),
`target.person_label` for the `user` target (`"Bob Builder"`), and
`actor.person_label` for an API-key actor (`"Unnamed user"`). A CLI actor has
`person` and both labels null.

**(h) MCP over HTTP.** `initialize`, `notifications/initialized`, then
`tools/call list_catalogs` with an admin key: each entry has `name`,
`display_name` and `label` (`heading-b` has `display_name: ""` and label
`Untitled catalog`), and `read_document` carries `catalog_label`.

No bug found. One thing a reader might trip on: a catalog with no display
name is labelled `Untitled catalog` but its heading is `# Catalog`, as
designed (#606).

## Issue #484

Issue #484 ("Setup email greets the user by account name instead of display
name") is delivered by #619: `Template::Setup { user }` is filled with
`user_label(display_name, email)` in `src/mail/invite.rs`, and the tests
`the_setup_email_greets_the_display_name` (text and HTML),
`a_hostile_display_name_is_escaped_in_the_setup_emails_html` and
`the_setup_email_falls_back_to_the_email_local_part_never_the_slug` cover it.
It differs from the issue in one way: with no display name the greeting uses
the email's local part, not the account name (the design never shows a
slug). The setup email is the only template that greets a user. The issue
stays open until the milestone reaches main.
