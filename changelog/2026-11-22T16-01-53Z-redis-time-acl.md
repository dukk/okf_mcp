# Shared rate limiter: find a Redis user that may not run TIME (issue #832)

## Fixed
- With a Redis user whose ACL lacks `TIME`, the `TAKE` script failed on
  every call and each replica fell back to its own bucket, with only a warn
  log per request to show for it.

## Added
- `shared::limits::check` runs the script once at start-up against a
  throwaway key. A refusal logs an error naming the ACL problem and never
  stops start-up (limits still work per replica).
- `/healthz` reports `rate_limits`: `shared`, `degraded` or `null` without
  `[redis]`. It never changes the status.
- `okf_ratelimit_fallbacks_total{limiter}` counts decisions a replica's own
  bucket made because the shared one failed.
- `docs/operations.md`: the Redis commands and ACL the server needs, `+time`
  in particular.

## Changed
- The fallback warning is logged at most once a minute per limiter.
- Exported events name the limiter `oauth_token` as `oauth-tok`
  (`Limiter::event_name`), so Sentry's scrubbing does not replace it with
  `[Filtered]`. Metric labels are unchanged.
- `TIME` stays in the script: dropping it would give up the single clock.

## Tests
- Against a Redis user with the production ACL string: the check fails and
  the limiter falls back, counted; with `+time` granted the check passes and
  the limiter is shared. `/healthz` reports a degraded limiter. The warning
  throttle. No exported limiter name contains "token".
