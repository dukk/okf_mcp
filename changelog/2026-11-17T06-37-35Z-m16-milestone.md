# Milestone 16: multi-replica serve (epic #553), close-out (issue #566, Task 13)

`okf-mcp serve` can run as several replicas behind one Service. An optional
`[redis]` table holds the short-lived state that lived in one process's memory,
and two caches learn of changes on every instance at once. Without `[redis]`
nothing changes. This entry is also Task 13's own changelog entry (the README
paragraph and the hand smoke test).

## Changed

Decisions (plan "Decisions taken while planning"):

1. Milestone 16 from issue #551; the spec is the design.
2. Redis is optional; without it one replica is still required.
3. Every `admin_generation` bump is published over pub/sub, from the reload
   that observes the bump (one place, after commit); the CLI publishes an
   empty announcement.
4. OAuth access tokens: a revocation counter in Redis checked on every lookup,
   seeded randomly when missing; 60 s cache age as the backstop. Pub/sub alone
   was rejected because messages are lost while a subscriber reconnects.
5. A finer task split: three foundation tasks, three OAuth tasks, the
   `authorize.rs` conversion and the CLI announcement as their own tasks.
6. CAS `update` for pending authorizations and codes; per-actor caps as index
   keys; the idle TTL refreshed in `bind_session`.
7. Passkey and OIDC link flows store only a hash of the console session id.
8. `/healthz` reports Redis (`"ok"`, `"unavailable"`, `null`) without changing
   its status code.
9. Every CLI command announces, read-only ones included.
10. The plan PR was merged by the coordinator after review.
11. Cluster mode for ElastiCache Serverless, added mid-milestone (2026-11-17,
    after Task 1 merged): production's cache is Valkey in cluster mode with
    TLS. `[redis] mode = "standalone" | "cluster"`, one hash tag on every key
    and channel in both modes, RESP3 push pub/sub in both modes. Supporting
    only cluster mode was rejected, so plain Redis and Valkey keep working.

### Smoke test (by hand, 2026-11-17)

Debug build of this branch's `okf-mcp`. Two `okf-mcp serve` processes per run,
on `127.0.0.1:18081` (with `public_url`) and `127.0.0.1:18082`, one Postgres
container, `poll_interval = "1h"` so only Redis can carry a change between
them, a Prometheus listener per process. The Redis password was generated and
never printed. Config (`mode` is `standalone` or `cluster`):

    poll_interval = "1h"
    public_url = "http://127.0.0.1:18081"
    [redis]
    url_env = "OKF_REDIS_URL"
    mode = "standalone"
    [telemetry.prometheus]
    listen = "127.0.0.1:19564"

Redis setups:

    # standalone
    docker run -d -p 127.0.0.1:16379:6379 --name <name> redis:7.4-alpine \
        redis-server --requirepass "$PW" --save "" --appendonly no
    # cluster (one node, no password; ports fixed so `docker start` keeps them)
    docker run -d -p 127.0.0.1:16380:6379 --name <name> valkey/valkey:8.1-alpine \
        valkey-server --cluster-enabled yes --cluster-config-file nodes.conf \
        --appendonly no --save ""
    docker exec <name> valkey-cli CONFIG SET cluster-announce-ip 127.0.0.1
    docker exec <name> valkey-cli CONFIG SET cluster-announce-port 16380
    docker exec <name> valkey-cli CLUSTER ADDSLOTSRANGE 0 16383
    docker exec <name> valkey-cli CLUSTER INFO | grep cluster_state   # ok

Results (all passed in both modes):

| Check | Standalone (Redis 7.4, `requirepass`) | Cluster (Valkey 8.1, one node) |
|---|---|---|
| initialize on :18081 (200, session id), `notifications/initialized` and `tools/list` with that id on :18082 | 202, then 42 tools | 202, then 42 tools |
| `okf-mcp key revoke <id>` (CLI, `poll_interval` 1 h): both ports answer 401 | 134 ms / 139 ms after the CLI started | 75 ms / 78 ms |
| `--scan --pattern '{okf:}*'` | `{okf:}mcp:bind:<64 hex>`, `{okf:}mcp:state:<64 hex>`; no raw session id or key | same |
| Redis stopped: `tools/list` | 503 on both; `/healthz` 200 with `"redis":"unavailable"` | same |
| `okf_redis_errors_total` after the outage | A 3 (`admit`, `get`, `subscribe`), B 2, from 0 | A 3, B 2, from 0 |
| Redis started again: service works, subscriber resubscribed | new session works; a key created and revoked afterwards by the CLI is seen and refused by both within 150 ms | same, once the announced port was re-applied (below) |

Trimmed output of the revoke check (the key is created, used, revoked):

    before revoke: A 200 B 200
    revoked key <id>
    port 18081 refused (401) 78 ms after the CLI started revoking
    port 18082 refused (401) 82 ms after the CLI started revoking

Trimmed output of the outage check:

    redis up: tools/list B 200; errors A=0 B=0
    redis stopped: tools/list A 503 B 503; healthz A: {"database":"ok","catalogs":1,"clock":null,"redis":"unavailable"} http 200
    okf_redis_errors_total after: A=3 B=2
    okf_redis_errors_total{operation="admit"} 1
    okf_redis_errors_total{operation="get"} 1
    okf_redis_errors_total{operation="subscribe"} 1

What running it taught:

- **A session does not survive a restart of an ephemeral Redis.** Both runs
  used `--save ""`, so the stopped container lost its data; the old session id
  then answers 404 (unknown session) and a client must initialize again. The
  checks above use a new session afterwards. A Redis with persistence keeps
  sessions.
- **`CONFIG SET cluster-announce-port` does not survive `docker start`.** The
  one-node cluster then names `127.0.0.1:6379` in `CLUSTER SLOTS`, which is not
  the mapped port, so the cluster client cannot follow it (the CLI warned
  "announcement skipped ... kind=Config" and a key created then was unknown to
  the servers, 401, until the next reload). Re-applying the announce port
  restored everything within 20 s with no restart of either `serve` process.
  This is a property of the test container, not of the server; Task 13's
  Corrected note in the plan says so.
- **The log shows no "key cache reload" line at `info` level** (the reload is a
  `debug` span), so resubscription was proved by effect: with `poll_interval`
  at 1 h, a key created and then revoked by the CLI after Redis came back was
  accepted, then refused, on both processes within 150 ms. Only a subscriber
  that was listening again could do that.
- **Standalone, one transient:** the first new key created about a minute
  after the restart was unknown (401) to both processes; the same check 2 min
  later passed, and it did not recur in a later run. The cause was not found;
  the likeliest is the interval between Redis returning and the subscriber's
  fresh `subscribe` (`RESUBSCRIBE_GRACE`, 10 s, plus reconnect backoff).
  A key change made inside that window reaches the other replicas at the next
  `poll_interval`, which is the documented backstop.
- Everything started was removed by name or pid: two Redis/Valkey containers,
  one Postgres container, four `serve` processes. Nothing was left listening.
