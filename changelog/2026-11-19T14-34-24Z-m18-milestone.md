### Settings added

`catalog_cache_bytes` (`"1GiB"`), `catalog_directory_entries` (100000), `catalog_ttl` (`"10s"`), `credential_cache_entries` (100000), `user_cache_entries` (100000), `credential_ttl` (`"10s"`), `overlay_cache_bytes` (`"256MiB"`), `search_fanout_max` (25), `worker_shutdown_grace` (`"30s"`).

### Settings deprecated (parsed, warned, ignored)

`poll_interval`, `overlay_cache_size` (use `overlay_cache_bytes`), `mail.worker` (every `serve` runs the worker). Removal is tracked in #727.

### Metrics added

`okf_cache_requests_total`, `okf_cache_evictions_total`, `okf_cache_load_duration_seconds`, `okf_cache_entries`, `okf_cache_bytes` (label `cache`: catalog, overlay, directory, credential, grant, user, labels), `okf_invalidations_queued_total`, `_received_total`, `_unreadable_total` and `_lag_seconds`, `okf_housekeeping_runs_total`.

## Changed

- **Response shapes.** `GET /api/v1/catalogs`, `/whoami` and `/labels` and MCP `list_catalogs` return one page with `next` (`?after=&limit=`; default 100, at most 1000); a client that read everything from one answer must follow `next`. `GET /api/v1/search` answers 400 past `search_fanout_max` catalogs when no catalog list is supplied (an explicit list is not capped, #725). `/healthz` reports `cached_catalogs` instead of `catalogs`. Unbuildable catalogs are left out of listings.
- **Removed metrics.** `okf_poll_duration_seconds`, `okf_catalog_refreshes_total`, `okf_catalog_concepts`, `okf_catalog_generation`, and the `okf.poll` span.
- Start-up loads no catalog; each loads on first use and is kept within `catalog_cache_bytes` (weight: 1 KiB per catalog, 1 KiB per file and 8 per stored byte).
- Changes reach other replicas through the change feed; the TTLs (`catalog_ttl`, `credential_ttl`) are the backstop. For one release the M16 bridge (`admin-generation` channel) keeps old and new replicas in step.

## Notes

### Scale test (`tests/scale.rs`)

Run once, alone, in release mode: `tools/agentic/gate.sh narrow --release --test scale -- --ignored --nocapture`. It seeds 1,000,000 catalogs (one 51-byte document each) and 1,000,000 users with one key each by SQL (about 40 s), against one throwaway Postgres 17 container on a shared machine. The last run, which passed (1 test, 127 s; the test also fails if a metric series is missing or a listing page is short or has no `next`):

| Bound | Measured | Result |
|---|---|---|
| `App::load` under 5 s, no catalog held | 1.2 ms (other runs 1.0 to 2.1 ms); `okf_cache_entries{cache="catalog"}` 0 | pass |
| 5,000 distinct catalogs read, budget fits 1,000 (2,456,000 B): `okf_cache_bytes{cache="catalog"}` never above budget | peak 2,456,000 (exactly the budget), 1,000 entries kept | pass |
| RSS growth under budget + 200 MiB (212,171,200 B) | 11,173,888 B (about 10.7 MiB) | pass |
| 10,000 distinct keys, p99 under 20 ms | p50 7.32 ms, p99 12.05 ms (Task 18); p50 0.34 ms, p99 0.55 ms (Task 19 run) | pass |
| credential entries at most `credential_cache_entries` (5,000 for the run) | 1,313 with the default 10 s `credential_ttl`; 5,000 (at the limit) with 1 h since #728 | pass |
| (Task 19) the administrator's first authentication, its team owning the million, under 20 ms | 3.20 ms (about 820 ms before #728) | pass |
| `GET /api/v1/catalogs`, admin key, first page | 96.4 ms first request (100 snapshots loaded one after another), 1.3 ms repeated | plan bound corrected, see below |

Things the runs showed, none hidden:

- **Authentication p99 is noisy on a shared machine.** Ten full runs (the first seven while the test was being fixed) gave p99 of 7.0 to 27.5 ms with p50 near 5.5 to 6.6 ms; the 20 ms bound was exceeded in two (27.5 and 26.6 ms) and held in eight, the two misses on a machine busy with other sessions. The test keeps the plan's 20 ms.
- **The first listing page missed the plan's 50 ms.** A default page is 100 catalogs, each loaded as a snapshot in turn, and the principal and labels load too: 80 to 96 ms cold, 1.3 to 1.5 ms warm. The page size bounds the number of snapshots loaded, so it should not grow with the catalog count; only this one size was measured. The test now asserts 200 ms for the cold page and the plan's 50 ms for the repeated page, and the plan carries a correction note. Loading a page's snapshots concurrently would be the fix if cold listings matter; it is not done here. Maintainer accepted the revised bound on 2026-11-19. Loading a page's snapshots concurrently is #732.
- **A first attempt measured 820 ms to authenticate the administrator.** The cause was the fixture: the million catalogs belonged to the administrator's own team, and a user's ceiling lists every catalog their teams own. The behaviour itself, a ceiling that grows with the catalogs a user's teams own, was filed as #728 and fixed as Task 19: the ceiling is resolved per catalog, and the seeded catalogs belong to the administrator's team again. A release run of the reworked test (2026-11-19, alone on the machine): the administrator's first authentication 3.20 ms (15 µs again), against about 820 ms before; 10,000 keys p50 0.34 ms, p99 0.55 ms; credential entries 5,000 at the 5,000 limit with `credential_ttl` 1 h; first listing page 18.65 ms, repeat 0.94 ms.
- The credential gauge settled at 525 to 1,803 entries after 10,000 distinct keys in the Task 18 runs, well under the 5,000 limit. Those runs used the default 10 s `credential_ttl`, so entries were expiring during the minute of authentications. With the TTL at one hour (#728's rework) the gauge holds 5,000, at the limit: the entry limit, not expiry, bounds it.

### Smoke test (by hand)

Two `okf-mcp serve` replicas (release binary, ports 18081 and 18082 on localhost) against one throwaway Postgres 17 container on 127.0.0.1, no Redis (the change feed carries the changes). User `alice`, catalog `smoke`, admin keys created with `okf-mcp key create ... --user alice`. A small stdlib Python client opened an MCP session on replica A and ran `open_changeset`, `create_concept` and `publish`; reads used `GET /api/v1/catalogs/smoke/concepts/...` and `GET /api/v1/whoami` on each replica.

1. Publish on A, read on B: B had already served the catalog (so it was cached), A published `two.md`, and B answered 200 for it at once. Later rounds repeated this (`three.md`, `four.md`, `five.md`): always 200 on B.
2. Revoke through the CLI (`okf-mcp key revoke <id>`) with the key warm on both replicas: `whoami` was 401 on both one second later.
3. Kill a replica's listener: `SELECT pg_terminate_backend(pid)` on the `LISTEN "okf_invalidate"` backend (the later-started of the two, replica B's, then both). Within 8 s there were two listeners again (reconnected). After the kill, publish on A and read on B: 200. Revoke through the CLI: 401 on both.
4. Hardest case: a fresh key warmed on both, both listener backends terminated, the key revoked immediately while both were down: both replicas answered 401 on the first check one second later (the reconnect's catch-up).

Everything was torn down afterwards: both replicas were stopped by PID and the container removed by name; no listener on the three ports remained.
