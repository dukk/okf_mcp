- One test per split statement, each on a fixture with two catalogs, two or more keys and a deleted key:

## Changed
- **Changeset listing** (`changesets::list_open`, `open_for_catalogs`, through the private `listed`). They take `(&AccountDb, &CatalogDb, ..)` and run in up to three steps instead of one statement joining `changesets`, `catalogs` and `api_keys`:
  1. when the list is narrowed by catalog name, the account database resolves the names (and any id filter) to catalog ids; an empty answer returns an empty list without a store query;
  2. the store reads the open changesets with their sorted paths (`changesets` and `changeset_entries`), filtered by the ids and the key;
  3. the account database returns the catalogs' names (`SELECT id, name FROM catalogs WHERE id = ANY($1) ORDER BY name`) and the keys' labels (`SELECT id, name FROM api_keys WHERE id = ANY($1)`), one query each over the distinct ids, so there is no per-row query.
  The final order is the old `ORDER BY k.name, c.updated_at, c.id`: a catalog's position in the name-ordered answer of step 3 is its sort key, so a database collation that does not order names bytewise gives the same list. A changeset whose catalog row is gone is left out (the inner join did that); one whose key row is gone gets `key_name: None` (the left join did that). The only caller, `mcp::changesets::list_changesets`, passes `App::accounts()` and `App::main_store()`.
- **A user's catalogs with open changesets** (`delete_checked`, now through the private `open_changeset_catalogs`): the user's key ids (`users`, `api_keys`), then `SELECT DISTINCT catalog_id FROM changesets WHERE key_id = ANY($1) AND state = 'open'`, then the catalogs' names ordered by name. It returns early on an empty step.
- **Discarding a deleted user's changesets** (`discard_open_changesets`): it takes the key ids `delete_checked` already read and locked (`SELECT id FROM api_keys WHERE user_id = $1 ... FOR UPDATE`) instead of joining `api_keys`. One statement reads the user's open changesets with their entry counts, in id order, `FOR UPDATE`; one reads the catalogs' names. It returns how many it discarded.
- **Claiming maintenance work** (`runs::claim`): it takes `accounts: &AccountDb` as a new first argument. Just before the `INSERT INTO maintenance_runs` it reads `SELECT id FROM api_keys WHERE id = $1` on the account database and binds the result as `key_id` (NULL when the row is gone), in place of the subselect. `credential_id` and `actor` are bound as before. Callers: `mcp::maintenance::work` passes `App::accounts()`; the tests pass `AccountDb::of`.
- **`repair::missing_root_index`** takes `(&AccountDb, &CatalogDb)`: the catalogs in name order (account), then the distinct catalog ids having a live root `index.md` (store), and the difference in Rust. The CLI's private `repair_targets` takes the same two handles; `catalog repair-indexes` builds its main-store handle before calling it.
- The plan (`docs/superpowers/plans/2026-11-23-okf-mcp-catalog-stores.md`) has a dated correction note after Task 5 (see Notes).

- **The deletion path runs on one transaction, not `main_store()`.** The plan says the store half of the two `users.rs` statements reads through `main_store()`. `delete_checked`'s transaction already holds the user's keys and takes `FOR UPDATE` on the changesets and writes audit rows, all in one transaction that in release 1 reaches both sides. A separate connection to the store could not take those row locks in that transaction's order, so the new statements use the transaction's connection. Each statement still names one side's tables. Task 13's fan-out has to split that transaction.
- **A race in `claim` that did not exist before.** The old subselect read the key and wrote the run in one statement. Now a key deleted between the account read and the insert (a window of one transaction's length at most) makes the insert fail on `maintenance_runs.key_id`'s foreign key (release 1 still has it), a database error the retry resolves (the transaction rolls back and the idempotency key is unused). Once Task 11 drops that foreign key, such a run records a key id that no longer exists, which is the same as the credential id it stores anyway.
- **Verified by reverting.** I changed each fix in turn and ran its test: dropping the catalog-name rank from the listing's sort, dropping `deleted_at IS NULL` from `missing_root_index`, discarding every keyed changeset instead of the user's, ordering a user's catalogs by id, and always recording the key id in `claim`. Each of the five tests failed. My first listing fixture passed with the sort reverted (its alpha changeset was also the oldest); I made it the newest so only the catalog name puts it first.
- Tests: the five above; the rest of the suite changed only in the `claim`, `list_open`, `open_for_catalogs` and `missing_root_index` calls.
