# M21 Task 4: maintenance takes `CatalogDb`

## Added
- Nothing new: this task only retypes entry points.

## Changed
- The public maintenance store functions take `&CatalogDb` instead of `&PgPool`, and begin their transaction with `CatalogDb::begin`:
  - `runs::list_runs`, `runs::get_run`, `runs::claim`, `runs::renew`, `runs::close`, and the crate-private `runs::snapshot` (the read-only snapshot transaction that `list_runs`, `get_run`, `reports::get_finding` and `reports::list_findings_with` share);
  - `reports::get_finding`, `list_findings`, `list_findings_with`, `count_findings` (its one statement runs on `db.executor()`), `dispose` and `submit`;
  - `evidence::read` (acquires a connection from `db.executor()`).
- Helpers that already took `&mut PgConnection` (`lock`, `replay`, `receipt`, `recover`, `candidates::load` and `cursors`, `evidence::validate`, `runs::page_ids`, `complete_if_terminal`, `expire_submission`, `reports::load_evidence`) are unchanged (P2).
- `src/mcp/maintenance/{reports,work}.rs` pass `App::main_store()`; the owner lookup in `work.rs` (a `SELECT credential_id FROM maintenance_runs`) uses `main_store().executor()`. `src/mcp/maintenance/mod.rs` and `src/maintenance/` hold no database call and needed no change.
- Tests: handle types only (`CatalogDb::main_of(&pool)` in the store's unit tests, `App::main_store()` in the HTTP test). Where a test passed the pool into `tokio::join!`, it builds one handle first, because the macro borrows its arguments.

## Notes
- No behaviour change: in release 1 `main_store()` and the account pool are one pool.
- Production callers of these functions are the maintenance tools in `src/mcp/maintenance/` only, so every one of them gets its handle from `App` through `ToolContext`. The HTTP routes in `src/http/api/maintenance.rs` call those tool functions. I grepped `src` and `tests` for other users of `store::maintenance` and found none outside tests. The CLI and the background workers do not call them; the maintenance runner in `src/investigator/` and `src/bin/okf-maintenance.rs` talks to the server over MCP and HTTP (I checked that neither imports the store; I did not read them line by line).
- **Crosses in release 1** (additions to the inventories in `changelog/2026-11-23T12-55-43Z-m21-task-02-catalog-writes-take-catalogdb.md` and `changelog/2026-11-23T13-36-45Z-m21-task-03-catalog-reads-take-catalogdb.md`; each line read from the code at this commit). Every maintenance table below is a store table after Task 11: `maintenance_state`, `maintenance_runs`, `maintenance_work`, `maintenance_findings`, `maintenance_evidence`, `maintenance_dispositions`, `maintenance_requests` (`migrations/0006_maintenance.sql`). The reads and writes of those tables, of `documents` and of `revisions` cross nothing.
  - **Registry lock at the start of every maintenance write.** `maintenance::lock` (`src/store/maintenance/mod.rs`) is called first in `runs::claim` (`runs.rs:457`), `runs::renew` (`:552`), `runs::close` (`:680`), `reports::dispose` (`reports.rs:295`) and `reports::submit` (`:444`). It calls `catalogs::lock` (`pg_advisory_xact_lock` keyed by `catalogs.id`, touches no table) and `changesets::lock_catalog` (`SELECT id FROM catalogs WHERE id = $1 FOR KEY SHARE`, an account table until Task 11; it returns `Refused(CATALOG_GONE)` when the row is gone). It then inserts into and locks `maintenance_state`. DONE in Task 11 (issue #970): `lock_catalog` locks `catalog_state`.
  - **The `api_keys` subselect.** `runs::claim` inserts into `maintenance_runs` with `key_id = (SELECT id FROM api_keys WHERE id = $3)` (`runs.rs:482`; `runs.rs:481` at `22c07f7`). The subselect reads `api_keys` and stores NULL when the key is gone. Task 5 splits it.
  - **DONE in Task 11 (migration 0041): foreign keys to the account tables** (`migrations/0006_maintenance.sql`): all seven `maintenance_*` tables have `catalog_id REFERENCES catalogs (id) ON DELETE CASCADE`, and `maintenance_runs.key_id REFERENCES api_keys (id) ON DELETE SET NULL`. So deleting a catalog cascades into these tables, and deleting a key (including through a user's deletion, `migrations/0013_user_deletion.sql`) nulls `maintenance_runs.key_id`, inside the account transaction. Task 11 drops both (its plan text drops the `key_id` one); Task 13 replaces the cascade with the store cleanup.
  - **DONE in Task 11 (`RunWatch` in `src/store/maintenance/mod.rs` replaces them): the audit triggers on `maintenance_runs`** (`maintenance_runs_audit_end`, `maintenance_runs_audit_empty`, function `audit_maintenance_run`, `migrations/0017_maintenance_audit.sql`). They fire inside these maintenance transactions whenever a run leaves `running` or is inserted already ended. The function reads `audit_credentials`, `api_keys`, `users` (through `api_keys`), `audit_teams` and `catalogs`, counts `maintenance_findings`, and inserts into `audit_entries` (an account table). The statements that fire them:
    - `runs::claim`: the `INSERT INTO maintenance_runs` at `runs.rs:482` when the selection is empty (state `completed`), and `recover` (below);
    - `recover` (`mod.rs`, called from `claim` at `runs.rs:470`, `renew` at `:576` and `close` at `:706`): the `UPDATE maintenance_runs ... state='failed'` at `mod.rs:150` and the `UPDATE ... state='completed'` at `mod.rs:168`;
    - `runs::complete_if_terminal` (`runs.rs:346`) and `runs::expire_submission` (`runs.rs:363`), both called from `reports::submit` (`reports.rs:481`, `:559`);
    - `runs::renew`'s `UPDATE ... state='completed'` (`runs.rs:604`) and `runs::close`'s `UPDATE ... SET state=$3` (`runs.rs:731`).
    Task 11 replaces the trigger with a Rust-side `catalog.maintenance_run` record, and Task 12 moves that write into the store transaction.
  - **No call to `audit::record`, `audit::lock_people` or the SQL functions `audit_person`, `audit_team_ref` and `audit_credential` from this module.** I grepped `src/store/maintenance/` for them; none is called (the trigger above is the only audit path).
- Reads that cross nothing: `list_runs`, `get_run`, `get_finding`, `list_findings`, `count_findings` and `evidence::read` read only the seven maintenance tables, `documents` and `revisions`. `candidates::load` and `cursors` read `documents`, `revisions` and the maintenance tables.
